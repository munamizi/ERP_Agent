# 采购分析

## 先确定本次要回答什么

简单询价、最低价、少量报价比较默认直接回复，不生成报告、图表或下载文件。报告和图表分别按需决定：用户要报告不代表要配图，用户要图也不代表要另写报告。当前明确要求优先于历史偏好；之前做过报告不等于本次也需要。

例如“买20个CPU补库存，先看看最低价”：本次目标是比较20个同型号CPU的可采购成本，不是创建采购单，也不需要销售单、缺料计划、历史趋势或供应商背景调查。没有到货日期时先完成当前询价，不把下单字段当成询价前置条件。匹配到多个不兼容型号且用户未选时，先说明并询问型号，不能混着比价。

若使用 Todo，只列实际需要的查询、报价比较和回复步骤，不固定加入报告、图表或导出文件。

## 查询和报价

- 先用 part_search 或 part_query 查询一次物料，获取 id、code、model 和 suppliers。供货关系已经包含 qualified，完整时直接复用，不再重复查询同一资料。ERP 负责业务数据，不要求它提供外部报价网址。
- 按本次需要抓取同型号候选供应商的报价。读取 /skills/procurement/web-scraper/SKILL.md，通过 execute 在远端沙箱运行抓取脚本；多家报价可在同一个脚本中并发请求。不能用 ERP 合同价冒充刚抓到的网页价。
- 原网页读取失败、报价缺失或过期时说明覆盖范围，不能声称比较了所有供应商或找到了全市场最低价。
- 只有缺少准入资料或确需详细供应商信息时才调用 supplier_query；需要背景调查时才用 web_search。
- 只有用户要求采购历史、趋势或历史价对照时才用 order_search_details。响应按采购单分组，明细在 lines；草稿和已取消订单不能当作成交历史。
- 只有用户关注库存风险时才查 inventory_warning。为明确销售单补料时才用 sales_order_query、sales_order_details 读取 mrp.items，采购量以 suggested_purchase_qty 为准；shortage 是实物缺口，可能已有按时在途覆盖。给定数量补库存不走这一步。
- 报价网址由 Agent 维护，不依赖 ERP 的 price_url。读取 /skills/procurement/supplier-price-urls/SKILL.md，通过沙箱 Python 按物料编码和供应商编号筛选映射，不必把全部映射读入上下文。映射缺失时说明缺口，或通过搜索核实来源，不按模拟站路径猜造真实网址。

## 计算实际采购成本

### 按本次任务编写并运行沙箱 Python

只为实际计算需要编写并运行 Python，使用 Decimal 计算金额。简单询价保留必要脚本输入和真实输出即可，不额外写 Markdown 报告或图表。复杂任务可按需求做历史趋势或有明确依据的加权评分，不固定套用一种公式。

同时核对供应商准入、型号、起订量、库存、交期、报价有效期、币种和税价口径。阶梯价按实际数量选取，不擅自多买；运费按真实交易条件说明。多家混合采购需要计算拆单运费，不声称简单单家排序等于全局最优。

保留脚本、输入和结果；脚本报错时修正并实际重跑。权重来自用户或明确声明的分析假设，不把主观评分说成 ERP 事实。仅做流程说明不算执行成功。

## 直接返回结果，按需补充交付物

简单询价给主 Agent 返回紧凑的 summary、suppliers（每项含 supplier_name）、recommendation：结论一句话，供应商数据只保留本次型号、数量、可采购单价和总额、运费及关键排除原因。币种、税价口径、来源和抓取时间集中说明一次。区分最低标价与满足实际数量约束的最低总成本，覆盖不全时限定结论范围；结论明确后结束查询。

内部交接保留必要证据和字段，不写完整报告式的“结论、证据、口径标注、建议、总结”多套重复内容，也不复制整页原文、完整工具 JSON 或脚本。需要引用时只给支持结论的短摘录；用户明确要求详细分析时再展开。

未生成文件时 report_path=null、chart_paths=[]，不能为了填这些字段调用工具。只有用户明确要求或已经确认的交付要求包含文件/图表时，才执行对应动作：

- 要报告：用 write_file 写 /analysis/report_<本次标识>.md，区分合同价、历史成交价、网页参考价和估算，返回真实 report_path。
- 要图表：先读 /skills/procurement/chart_params.md，再调用 generate_visualization。返回真实 chart_paths；本地 HTML 可导出，远端服务结果按实际返回交付，不当作本地文件。

## 需要下单交接时才生成采购方案

用户明确要求后续下单或可执行采购方案时，才补充 purchase_plan 和 missing_info；仅询价不构造完整下单字段。purchase_plan 按供应商拆分，每单包含：

- supplier_id、sales_order_id（备库存采购可为空）、expected_date。
- lines：每行只含 ERP part_id、quantity、元字符串 unit_price，与 ERP 请求字段一致。
- freight：整单运费；evidence 另存型号、来源网址、抓取时间及实际需求依据。

先将网页的 part_code、型号和 ERP part_id 对齐再填写明细，不能把物料编码当内部 ID。缺交期、编号或可行报价时，将未知项列入 missing_info，不猜日期或生成虚假的完整方案。没有满足条件的方案时 purchase_plan 为空。

用户明确要求采购后，由主 Agent 将方案和操作意图交给订单子 Agent；本 Agent 的建议不代表用户授权。
